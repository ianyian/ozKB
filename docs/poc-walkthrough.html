Shopfloor KB Hub

One searchable knowledge base that connects every FlexPM change request to the code that implemented it, across every site. Engineers can find a function, see why it was built, see where else it runs, and catch duplicates before they are built again. Everything runs on self-hosted, open-weight software that can move from rented AWS servers to company hardware.

~46 GBraw attachments (20k × ~2.3 MB)

What this POC proves in 14 weeks
  • We can link CRs to code automatically with a measured, labelled confidence.
  • An LLM can write accurate knowledge cards, checked by domain experts.
  • Search and AI answers beat today's manual hunting on 100 real engineer questions.
  • The real cost of a full 20,000-ticket backfill, measured on 300 pilot tickets instead of guessed.

1 · My understanding of the requirement

Knowledge exists, but it is split across two systems and lost people

Restated in my own words so we can confirm we mean the same thing before any code is written.

The problem

FlexPM holds the why: CR tickets, revisions like 121648-02, specs, slides, customer drafts and edit history. Azure DevOps holds the how: repos, PRs, commits. The link between them is complete only for newer repos named <Region>-<Customer>-FLEXPM<Task>-<Feature>. Older code has partial or no links, and code is often copied to other sites with no new CR at all.

The result: engineers can't find existing functions, can't explain old code after its author leaves, and build the same thing twice.

What engineers must be able to do

  1. Find a function, spec or requirement fast, by keyword, ID or code symbol.
  2. Understand what it does and why, as the requirement stood at the time it was built.
  3. Locate every other site, project and version that has it.
  4. Detect duplicates before building again.
  5. Trace both ways: requirement → code and code → requirement.

What makes this hard

Incomplete linkageOnly part of the code is linked to a CR. The system must infer the rest and say clearly that it is inferred (N4, D7).
Invisible copiesPlug-and-play reuse leaves no trace in FlexPM. It can only be found by comparing code itself (F7, clone detection).
"As it was" answersThe requirement and code at implementation time, not today's version. Needs commit-level links and ticket edit history (F6, D8).
Complete lists"Which sites have X?" needs every site, not the top 5 search hits. Vector search alone can't do this, so a link database answers it (F8, D5).
Self-hosted onlyNo managed AI or search services. Open-weight models on our own GPUs, portable to company servers (N1, N2).
TrustEvery AI statement must point to a ticket, file, line range or commit (N3). Experts review low-confidence items (F10).

Core idea: one knowledge card per task revision merges the CR requirement with the linked code logic. Cards are the first thing search and the agent read. Real code and documents stay indexed underneath, for exact detail and verification.

3 · How CRs and code get connected

Every link carries its evidence and a confidence level

Historical linkage is messy, so we never present a guess as fact. Each link records how we know it. The example below shows one function's real-world life: built, revised, copied without a CR, and rebuilt independently at another site.

CONFIRMED

Repo name contains FLEXPM<id>, or a PR / work item links the CR.

Shown as fact.
STRONG

CR number in a commit message, branch name or code comment. Also: an expert confirmed an inferred link.

Shown, marked strong.
INFERRED

LLM compares CR text with the code change, using time, developer and files as hints. Or clone detection finds a copy.

Marked inferred; sampled weekly for review.
UNLINKED

No evidence found on either side.

Recorded as a knowledge gap, still gets a card.

Clone detection classifies each match as exact copy (same normalized AST hash), modified variant (MinHash/LSH similarity over normalized tokens), or independent re-implementation (different code, similar requirement found by embedding similarity of CR text). The first two build code lineage; the third is the duplicate the business wants to stop.

4 · Review of the requirement

Strong design, with gaps to close before approval

The profile is well thought out. The points below are what I would change or add. High items affect whether the POC answers the business question or whether we are allowed to run it at all.

KEEPOne card per task revision, revision chain, card history. Matches how FlexPM actually works.
KEEPThree stores (link DB, search, code search). Each fixes a real weakness of vector-only RAG.
KEEPConfidence tiers with evidence, and links to commits rather than files.
KEEPOne incremental pipeline; backfill is a replay. No two systems that disagree.
KEEPPhases 1–3 deliver search value before any AI answering.
KEEPCard first, code on demand. Cards are summaries; code stays the ground truth.

6 · POC plan

14 weeks, four go/no-go gates

Same phases as the profile, with a Phase 0 added and the golden question set moved to the start, so every later phase is measured against a baseline. Each gate has numeric pass criteria; the numbers are my proposal for discussion.

G1 · Foundation

end of week 4
  • ≥ 98% of pilot tickets and attachments normalized without errors
  • Git mirror complete; size and repo count known
  • Confirmed-link coverage measured and reported (% of CRs with a confirmed repo/PR)
  • Secret scan run; findings redacted

G2 · Card pilot (300 tickets)

end of week 8
  • Expert rating ≥ 4 of 5 on 50 sampled cards
  • ≤ 2% of card statements fail the citation check
  • Measured tokens per card and GPU-hours per 1,000 cards → full backfill cost known

G3 · Search release

end of week 10
  • Golden set: right item in top 10 for ≥ 85% of lookup questions
  • Exact IDs and code symbols jump straight to the item: 100%
  • Search p95 latency under 1.5 s
  • Pilot users rate it better than today's way of searching

G4 · AI release

end of week 13
  • Answer correctness ≥ 75% on the golden set, graded by experts
  • Citation correctness ≥ 95%
  • Inferred-link precision ≥ 80% on 100 sampled links
  • List/count questions match the link DB exactly
